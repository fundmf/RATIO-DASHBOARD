BTC

Long-term BTC charts — supply in loss, 200-day moving average, and correlation with NASDAQ 100
BTC Supply in Profit or Loss (% of Supply) ↗ Open full chart on CheckOnChain

In plain English: Every bitcoin has a "last-moved price" (roughly, the price when it was last spent to its current wallet — a proxy for cost basis). This chart splits the total BTC supply into two bands: coins currently in profit (last-moved below today's price) and coins currently in loss (last-moved above today's price). A rising red/loss band = holders getting underwater (capitulation risk). A large green/profit band = market euphoria/top risk.

Source: CheckOnChain — free public on-chain dashboards published by James Check (@_Checkmatey_), a respected on-chain analyst and former Glassnode lead. Chart data derived from Bitcoin's public blockchain (UTXO set) — no paid API required.
Method (short): Every bitcoin UTXO's price at last movement is compared to the current spot price. Coins with last-move price below spot are counted as "in profit"; above spot = "in loss". Aggregated to a daily snapshot and stacked as % of circulating supply.
Interactive: Hover for exact values, use the toolbar in the top-right of the chart to zoom/pan.
BTC Price vs 200-Day Moving Average Loading…

In plain English: The 200-day MA is the average of BTC's daily closes over the last 200 days. Price above the MA = long-term uptrend. Price below the MA = long-term downtrend. Historically one of the most-watched "regime" signals in crypto.

Source: Binance public klines API — the largest global crypto exchange by volume; the industry-standard reference for BTC price data.
Method: Fetches the last 300 daily candles (BTCUSDT), plots the close price as a solid line and the trailing 200-day simple moving average as a dashed line.
BTC vs NASDAQ 100 (365-day % Return) Loading…

In plain English: Both assets are rebased to 0% on the first day shown, then tracked as cumulative % change. If the lines move together, BTC is trading like a tech stock. If they diverge, BTC is behaving independently (e.g. driven by crypto-specific catalysts).

Sources: BTC — Binance daily klines. NASDAQ 100 (^NDX) — Yahoo Finance daily chart data (via our /api/yahoo proxy).
Method: Both series are aligned by trading date (Yahoo skips weekends/holidays — we align BTC to those same dates), rebased so day-1 = 0%, then plotted as (price / baseline − 1) × 100.

🚀 First-Time Setup (do this once, takes ~10 minutes)

Follow these steps in order. If you stumble on any step, scroll to the Troubleshooting section at the bottom.

1
Install the ntfy app on your phone
iOS: open the App Store, search ntfy, install the one with the orange bell icon by Philipp Heckel.
Android: Play Store → search ntfy. Same icon, same developer.
Both versions are free, open source, and no account is required.
2
Pick a unique "topic" name
A topic is just a string — it's the address of your alert channel. Anyone who knows the string can send and receive on it, so make it unguessable. Treat it like a low-stakes password.

Good examples: rr-crash-team-7k9m2x · fartcoin-alerts-x4z9p
Bad examples: test · btc · alerts (too generic — other people might be using these)

Write your chosen topic down — every team member who wants alerts will need it.
3
Subscribe to the topic in the app
Open the ntfy app → tap the + button (bottom-right) → type your topic name → leave the server field as the default (ntfy.sh) → tap Subscribe.

iOS only — important: after subscribing, the app will ask permission for Critical Alerts. Tap Allow. This is the one thing that makes the alarm wake you up even when your phone is on silent or Do Not Disturb. If you accidentally tapped Deny, go to iPhone Settings → ntfy → Notifications → toggle on Critical Alerts.

Every team member who wants the wake-up alert must do steps 1–3.
4
Add CRON_SECRET to Cloudflare (one person only — admin)
This step is for whoever owns the Cloudflare account. It's a one-time setup.

a. Go to dash.cloudflare.com → Workers & Pages → click this dashboard's project.
b. Settings tab → Variables and secrets.
c. Click + Add:
  • Type: Secret (encrypted)
  • Name: CRON_SECRET
  • Value: any random string. Generate one at random.org/strings — use 20+ characters, alphanumeric. Save it somewhere you can find it (e.g. password manager) — you'll need it in step 5.
d. Save → go to Deployments tab → on the latest deployment, click the ⋯ menu → Retry deployment. The new env var only takes effect after redeploying.
5
Set up the 1-minute cron job
The cron is what actually checks the price every minute. We use cron-job.org — free, supports 1-minute polling.

a. Sign up at cron-job.org (free, ~30 seconds — they email you a confirmation).
b. Once logged in, click CREATE CRONJOB (top right).
c. Fill in:
  • Title: "Crypto crash check" (anything you'll recognise later)
  • URL: https://<your-pages-domain>/api/crash-check?key=<PASTE_CRON_SECRET>
    Replace <your-pages-domain> with the dashboard's URL (e.g. ratio-dashboard.pages.dev) and <PASTE_CRON_SECRET> with the secret you generated in step 4.
  • Schedule: Every minute (advanced → cron expression * * * * *)
  • Request method: GET
d. Save → make sure the toggle next to the job is ON (green).
6
Configure on this tab
Scroll back up to the Live Monitor card and:
a. Type your ntfy topic name (the one from step 2).
b. Choose the coin to monitor — any Binance ticker (BTC, FARTCOIN, DOGE, …). The status strip should immediately show a live price.
c. Adjust drop %, window minutes, cooldown to taste. Defaults (8% / 10 min / 60 min) are a sensible starting point.
d. Optionally set a floor price — useful if a coin has already crashed and you don't want bounces alerting you.
e. Click 📲 Send test push to my ntfy topic. Your phone should buzz within ~5 seconds. If it does, ntfy is working.
f. Once the test push works, tick Enable crash monitoring.

That's it — you're live. The cron will start firing alerts whenever the threshold is breached.
📋 How the data and triggers work

Full transparency on data sources, request volumes, and the exact alert math.

Data source

  • Primary: https://fapi.binance.com/fapi/v1/klines — Binance USDT-margined perpetual futures, 1-minute candles. Public API, no key needed.
  • Spot fallback: https://api.binance.com/api/v3/klines — automatically tried if futures returns 400/404 (e.g. coin only listed on spot, not on perps).
  • Symbol format: <COIN>USDT — typing DOGE requests DOGEUSDT, typing FARTCOIN requests FARTCOINUSDT, etc.
  • Request weight: 1 per call. Binance allows 2,400 weight per minute per IP. At 1 call per minute we use 0.04% of the budget — virtually impossible to hit a limit.
  • Timeout: 8 seconds per request via AbortController. Slow/hung requests don't lock up the worker.
  • No API key required, so no key rotation, no expiry, no secret to leak.

Trigger logic

windowHigh = max(high of last N 1-min candles, where N = window minutes) currentPrice = close of latest candle dropPct = (windowHigh - currentPrice) / windowHigh × 100 FIRE alert if ALL conditions met: crash_alert_enabled == true AND dropPct >= drop_threshold AND (floor_price == null OR currentPrice >= floor_price) AND (now - last_alert_time) >= cooldown_min × 60s

The floor price input suppresses alerts when the price is already below a configured level — useful for already-crashed assets bouncing on noise. Leave blank to disable.

Status strip — what each value means

  • 🟢 Monitoring — alerts enabled, drop below threshold, no recent fire. Healthy.
  • 🟡 In cooldown — an alert recently fired, we're suppressing new ones until the cooldown elapses.
  • 🔴 Threshold breached — drop is currently above threshold; next cron tick (within 60s) will fire the alert.
  • ⚪ Disabled — monitoring is off. No alerts will fire.
  • ⚠ No data — Binance doesn't recognise the symbol. Try a different coin.

The "Last refreshed" timestamp updates every 30 seconds — the dashboard itself polls Binance from the browser to show live status. This is independent of the cron, so the dashboard works even if the cron is paused.

🛠 Troubleshooting

"Send test push" doesn't reach my phone

  • Check your phone has the ntfy app installed and is subscribed to exactly the same topic string (case sensitive, no typos)
  • Check the phone has notifications enabled for the ntfy app (Settings → Apps → ntfy → Notifications)
  • Check the phone has data/Wi-Fi
  • iOS: check Critical Alerts is granted (Settings → ntfy → Notifications → Critical Alerts)

Status shows "⚠ No data for XXXUSDT"

  • The coin isn't listed on Binance under that symbol. Try a different one, or check Binance's listings page for the correct ticker.

Status stays "⚪ Disabled" after I ticked enable

  • The save may have failed (e.g. no connectivity at the moment of saving). Tick it off and on again, watch the small status text at the right of the buttons — should say "Saved." briefly.

Alert spams during a sustained crash

  • Increase the cooldown minutes. Default 60 means at most 1 alert per coin per hour even if it keeps dropping.

I don't think the cron is running

  • Log into cron-job.org → click your job → check the Execution history tab. You should see one entry per minute with HTTP 200.
  • If you see 403 responses, the CRON_SECRET in the URL doesn't match the env var on Cloudflare — copy-paste from your password manager carefully.
  • If you see 5xx errors, hit the URL manually in your browser (without the key) — should return {"error":"forbidden"} if the function is at least reachable.

Forgot my CRON_SECRET

  • Cloudflare doesn't show secret values once saved. Generate a new one (Cloudflare → Variables and secrets → edit CRON_SECRET → paste new value → save → redeploy), then update the cron-job.org URL with the new secret.

1. Ratio Analysis

Compares how far the current price of each asset is from user-defined key levels (highs/lows). Tracks two pairs: BTC & MSTR and ETH & BMNR.

Data Sources & Frequency

  • Historical: data.json — daily close prices, updated hourly via GitHub Actions using update_data.py
  • Live: CoinGecko API (BTC, ETH) and Yahoo Finance via Cloudflare proxy (MSTR, BMNR) — fetched on page load

Graph 1 & 2: Ratio Charts

Each chart plots 4 lines representing how far the current price is from each key level, as a ratio:

Ratio = Key Level Price / Current Market Price
  • A ratio of 1.0 means the price is exactly at the key level
  • A ratio above 1.0 means the price is below the key level (room to rise)
  • A ratio below 1.0 means the price has surpassed the key level
  • Red dots mark the extreme points (max for HIGHs, min for LOWs) with the dollar price at that moment

Key Price Levels

Auto-calculated from the selected date range: BTC HIGH = max high price, BTC LOW = min low price, etc. All 8 inputs are manually editable.

High/Low Distance Charts

Plots the gap between the two assets' ratio lines over time:

HIGH Distance = (BTC HIGH / BTC price) − (MSTR HIGH / MSTR price) LOW Distance = (BTC LOW / BTC price) − (MSTR LOW / MSTR price)

When these lines diverge, the two assets are moving apart at their extremes. Same logic applies for ETH/BMNR.

BTC/MSTR Spread Divergence

Combines the HIGH and LOW distances into a single volatility-normalised metric:

Raw Ratio = HIGH Distance / LOW Distance Vol-Adjusted = Raw Ratio / 20-day Rolling StDev
  • Above 0: Highs diverging faster than lows
  • Below 0: Lows diverging faster than highs
  • Dividing by rolling volatility (not z-score — no mean subtraction) puts all time periods on equal footing
  • Minimum 5 valid data points required in the 20-day window

Controls

  • AEST toggle: Shifts displayed dates +1 day (US market close = next morning AEST)
  • Reference line: Toggles a red dashed line at ratio = 1.0
  • Date range: Independent for Graph 1 and Graph 2

Combined View — Standardised Volume Comparison

Three-panel stacked chart with synchronised hover across all panels:

  • Top panel: BTC price (amber) + FARTCOIN price (green) — dual Y-axes
  • Middle panel: BTC volume as z-score
  • Bottom panel: FARTCOIN volume as z-score

4. FARTCOIN Analysis

Detects divergence events where BTC drops but FARTCOIN holds positive over a 24-hour lookback, then tracks whether FARTCOIN crashes within 72 hours.

Data Source

  • fartcoin_hourly.json — hourly BTC + FARTCOIN prices from CoinGecko, updated hourly by backfill_hourly.py
  • Live data appended from CoinGecko on page load

Event Detection Logic

For each hour i (where i ≥ 24): BTC change = (BTC[i] − BTC[i−24]) / BTC[i−24] FART change = (FART[i] − FART[i−24]) / FART[i−24] Divergence detected if: BTC change ≤ −threshold AND FART change ≥ 0
  • Clustering: Consecutive divergence hours with gaps ≤3 hours are grouped into a single event
  • Deduplication: One event per calendar day (AEST)
  • Confirmation window: 72 hours from the end of the divergence cluster
  • Crash %: (peak price − min price) / peak price × 100
  • Confirmed if crash % ≥ crash threshold

Default Thresholds

  • BTC drop: 1.5% over 24 hours (configurable 0.5-10%)
  • FARTCOIN crash: 5% within 72 hours (configurable 1-50%)

Chart Overlays

  • Red zones: Divergence period (BTC down, FARTCOIN holding) — crash followed
  • Green zones: Confirmed crash window (crash ≥ threshold within 72hrs)
  • Amber zones: Divergence detected but no crash followed

Statistics

Divergence count, confirmed crashes, hit rate (confirmed / total), and average crash % for confirmed events.

7. AI Affected Stock Watchlist

Tracks weekly Friday-close returns for a curated list of AI-exposed equities against the NASDAQ 100 benchmark. A new data point is captured every Friday after US market close (4pm ET).

Tickers

  • GTLB — GitLab Inc.
  • CDW — CDW Corporation
  • ADBE — Adobe Inc.
  • EXLS — ExlService Holdings
  • ADP — Automatic Data Processing
  • NASDAQ100 (^NDX) — benchmark, plotted as a dashed grey line

Data Source & Update Schedule

  • update_ai_watchlist.py runs in its own workflow (update-ai-watchlist.yml) on a weekly cron — Saturday 02:00 UTC, with Sunday and Monday 02:00 UTC as backup runs
  • On each run, it determines the most recent Friday whose 21:00 UTC cutoff has passed (safe across DST — covers both 4pm EST = 21:00 UTC and 4pm EDT = 20:00 UTC)
  • If that Friday is not already in ai_watchlist.json, it fetches close prices via yfinance and appends one record
  • Idempotent — once that week's data is recorded, the Sunday/Monday backup runs are no-ops

JSON Structure (ai_watchlist.json)

{ "last_updated": "ISO timestamp", "tickers": ["GTLB", "CDW", "ADBE", "EXLS", "ADP", "^NDX"], "labels": {"GTLB":"GTLB", ..., "^NDX":"NASDAQ100"}, "baseline_date": "YYYY-MM-DD", // first Friday captured "weeks": [ {"date": "YYYY-MM-DD", "closes": {"GTLB": 45.23, "CDW": 178.5, ...}} ] }

Chart Logic

  • Baseline = the first Friday in weeks (typically the Friday before this tab was deployed)
  • Y-axis: cumulative percentage return from baseline: (close[i] − baseline_close) / baseline_close × 100
  • X-axis: Friday dates (one per data point)
  • NASDAQ 100 line is dashed to visually distinguish the benchmark from individual names
  • Snapshot card below the chart sorts tickers by current return (best → worst)
When freshly deployed, the chart shows a single data point (the baseline) and all returns equal 0%. The first non-trivial chart will appear after the next Friday close.

Adding or Removing Tickers

Designed to be edited in one place. Open update_ai_watchlist.py and edit the TICKERS dict near the top:

TICKERS = { "GTLB": "GTLB", "CDW": "CDW", # ... add or remove lines here ... "NVDA": "NVDA", # add Nvidia "^GSPC": "S&P500", # add S&P 500 index }
  • Adding: On the next workflow run the script will automatically backfill the new ticker's Friday close for every existing week, so it lines up with the baseline and the chart immediately shows it with full history.
  • Removing: Delete the line and push. Removed tickers disappear from the chart and snapshot on next save. Historical values stay in ai_watchlist.json in case you want to add them back later.
  • Colors: Known tickers use a curated color in AI_COLORS. Unknown tickers automatically receive a unique color from AI_PALETTE (10-color rotation). No JS edit required.
  • Display label: The dict value (e.g. "NASDAQ100") is the legend label. Yahoo's symbol (e.g. ^NDX) stays internal.

Manual Trigger

To pull the latest Friday immediately (or to test after editing TICKERS), go to GitHub → Actions → "Update AI Watchlist (Weekly)" → Run workflow. The script is idempotent so this is always safe.

  • KuCoin — api-futures.kucoin.com (8h)
  • Hyperliquid — api.hyperliquid.xyz (1h)

SPX and FARTCOIN are largely Hyperliquid-native — exchanges that don't list them simply fail silently and don't contribute to the average. Each card shows the actual contributor count (e.g. "avg of 8 exchanges" vs "avg of 1 exchange").

Aggregation Math

For each exchange where the coin is listed: annualised = native_rate × (24 / funding_period_hours) × 365 Aggregate = mean(annualised across exchanges) Display rate (% per hour) = Aggregate / 8760

Normalising to annualised first handles the 1h vs 8h period mismatch correctly. The "per hour" display value is the hourly equivalent of the annualised average, so the card layout matches the original single-exchange view.

Cadence

  • funding_rates.py runs once daily on cron 0 21 * * 1-5 (21:00 UTC Mon-Fri = 4pm EST / 5pm EDT, DST-safe) in its own workflow (update-funding.yml)
  • Idempotent — re-running the same day is a no-op
  • JSON keeps the last ~120 weekday snapshots (~6 months); each snapshot includes a per_exchange breakdown for traceability

Slack Alert Trigger

  • Same script, same daily run — if the aggregate rate is < 0 for any enabled coin, a Slack message is posted naming the contributing exchanges and showing the annualised %
  • Dedupes per coin per UTC date — at most one alert per coin per day
  • Per-coin toggles live at the bottom of the Funding Rates tab and write to notification_settings.json via /api/settings

Adding More Coins or Exchanges

Edit the COINS list or EXCHANGES registry in funding_rates.py. Each exchange entry needs a fetcher function, a funding-period in hours, and per-coin trading symbols. The frontend reads coin keys from funding_rates.json, so chart and cards update automatically.

7c. BTC ETF Flows (Market Liquidity tab)

Scrapes farside.co.uk/btc/ daily, stores history in etf_flows.json, and sends a Slack alert when consecutive days' net flows flip sign with a magnitude above a configurable threshold.

Alert Logic

Alert fires when ALL of these are true:

  • Yesterday and today have opposite signs (one positive, one negative)
  • |today − yesterday| ≥ threshold (default $300M)
  • Alert is enabled in settings
  • Today's date has not already triggered (dedupe by date)
Examples (threshold = $300M): Y = −$200M, T = +$200M → flip, |Δ| = $400M → ALERT (turned positive) Y = +$50M, T = −$300M → flip, |Δ| = $350M → ALERT (turned negative) Y = +$50M, T = +$500M → no flip → no alert Y = −$50M, T = +$200M → flip, |Δ| = $250M → no alert (below threshold)

Cadence

  • etf_flows.py runs in its own dedicated workflow (update-etf-flows.yml) on a daily cron — 04:00 UTC primary, 06:00 UTC backup, 10:00 UTC second backup
  • The triple-cron is for GitHub Actions reliability — their scheduler regularly drops individual scheduled runs, so multiple cron times ensure the daily capture & alert don't get lost
  • The script is idempotent — once the latest day is recorded and the alert is dispatched, subsequent runs that day are no-ops (no double-alerts, no extra Farside requests beyond the dedupe check)

Configuration

The toggle and the dollar threshold are editable inline on the Market Liquidity tab's BTC ETF Flows card. Both save via /api/settings and take effect on the next scrape.

7d. Real-Time Crash Alert

Polls a coin's 1-minute price candles every minute. If the drop from the highest high in the window exceeds the configured threshold, fires an ntfy URGENT push — a loud wake-up sound on phones with the ntfy app installed. Cooldown prevents spam during sustained crashes. No Slack on this alert — by design, ntfy is the only channel because it's the one that actually wakes you up.

Architecture

  • Endpoint: functions/api/crash-check.js — Cloudflare Pages Function
  • Polling: External cron service (e.g. cron-job.org free tier, 1-minute resolution) hits https://<your-domain>/api/crash-check?key=<CRON_SECRET> every minute
  • Data source: Binance public klines — futures first (fapi.binance.com/fapi/v1/klines), with spot fallback (api.binance.com/api/v3/klines) if the coin isn't on futures. Each call costs 1 weight against Binance's 2400/min limit — at 1 req/min we use 0.04% of the budget
  • Reliability: 8-second per-request timeout via AbortController; spot fallback handles delisted/spot-only coins; no API key needed so no key rotation risk
  • Coin coverage: any symbol tradable on Binance as <COIN>USDT. The script tries futures first, then spot — so coins like BTC/ETH/SOL/DOGE/FARTCOIN/SPX all work out of the box. Custom small-cap spot-only listings work too via the fallback.
  • Settings: read from notification_settings.json via GitHub API (same pattern as /api/settings)
  • Cooldown state: persisted in crash_alert_state.json via GitHub API — only updated when an alert fires (no per-minute heartbeat writes, so the repo doesn't fill with noise commits)
  • Live dashboard status: the card on the FARTCOIN Analysis tab fetches Binance directly from the browser every 30s and shows current price, current drop %, status (Monitoring / In cooldown / Threshold breached / Disabled), and last alert time. This is independent of the cron — so the dashboard works for verification even if the cron is down

Detection Logic

windowHigh = max(highs over last N 1-min candles) currentPrice = latest close dropPct = (windowHigh - currentPrice) / windowHigh × 100 if dropPct ≥ threshold AND not in cooldown: fire ntfy URGENT + Slack record cooldown timestamp

The floor price input (optional) suppresses alerts when the coin is already below a configured value — useful for already-crashed assets bouncing on noise.

Notification Channel

  • ntfy URGENT only: POST to https://ntfy.sh/<your-topic> with Priority: urgent header. On Android plays a continuous loud alarm; on iOS uses Critical Alerts (bypasses silent/DND if the user grants permission)
  • Slack is deliberately not used here — the existing Slack-based alerts (funding flip, ETF flip) are for situational awareness during business hours, while this is for genuine wake-up emergencies. Mixing them would dilute Slack's signal-to-noise.

One-Time Setup

  1. Each team member who wants alerts: install the ntfy app (iOS/Android, free), open it, subscribe to the topic name you chose on the dashboard (e.g. fartcoin-crash-team). On iOS, grant Critical Alerts permission when prompted.
  2. Cloudflare Pages env vars (Pages project → Settings → Variables and Secrets, mark as Secret):
    • CRON_SECRET — any random string, used to authorise the cron service
    • GITHUB_PAT / GITHUB_REPO — already configured for /api/alerts and /api/settings, reused here
    • SLACK_WEBHOOK_URL — already configured
  3. External cron: sign up at cron-job.org (free), create a job:
    • URL: https://<your-domain>/api/crash-check?key=<CRON_SECRET>
    • Schedule: every 1 minute
    • Method: GET
  4. On the dashboard: FARTCOIN Analysis tab → Crash Alert card → set the threshold/window/cooldown/floor/coin/ntfy-topic → tick "Enable crash monitoring" → click "Send test push" to verify your phone receives it.

Security

The /api/crash-check endpoint bypasses the dashboard's password gate but requires ?key=<CRON_SECRET> for any request to be honoured. Without the key it returns 403. Keep CRON_SECRET secret — anyone with it can trigger a check (which costs nothing but could fire an alert).

Defaults / Safety

  • crash_alert_enabled defaults to false — you have to actively enable it on the dashboard, so an unconfigured deploy won't fire any alerts
  • ntfy_topic defaults to empty string — if not set, the endpoint returns a clean "ntfy_topic not set" message rather than alerting
  • Window has a 2-minute minimum; cooldown has a 1-minute minimum (input validation)

8. Custom Alerts

Schedule team reminders that get sent to Slack at the specified time.

How It Works

  • Fill in a title, date/time, timezone, and optional description
  • Alert is saved to localStorage (instant display) and to custom_alerts.json in the repo via the /api/alerts Cloudflare Function (uses GitHub Contents API)
  • GitHub Actions runs custom_alerts.py every hour — if an alert's UTC time is within 30 minutes of now, it sends a Slack message via SLACK_WEBHOOK_URL_CUSTOM
  • Slack message shows both the original timezone and AEST conversion
  • Sent alerts auto-clean after 7 days

Timezone Handling

UTC conversion (frontend): 1. Interpret datetime as UTC guess 2. Format that UTC time in the target timezone via Intl.DateTimeFormat 3. Calculate offset = (formatted tz time) − (UTC guess) 4. Result UTC = UTC guess − offset

Supported timezones: AEST (Sydney), ET (New York), CT (Chicago), PT (Los Angeles), GMT (London), UTC, JST (Tokyo), SGT (Singapore).

Multi-User Sync

On tab load, alerts are fetched from the server and merged with localStorage. Server-side "sent" status is synced to local. Alerts created by other team members appear after a page refresh.

9. Slack Alert Systems

All automated alerts run hourly via GitHub Actions (cron 0 * * * *). Two separate Slack channels are used.

Channel 1: SLACK_WEBHOOK_URL

Receives three types of alerts:

a) Divergence Events (detect_events.py)

  • Runs all 4 divergence analyses (FARTCOIN, Inverse FARTCOIN, SPX6900, BTC/FC→SPX) against hourly data
  • Alerts on new events only — compares against last_events.json
  • Dedup key: event_type:AEST_date (one event per type per day)

b) Market Alerts (market_alerts.py)

  • Oil data: Hyperliquid xyz:BRENTOIL (Brent, 24/7). Nasdaq data: Yahoo Finance ^NDX (US-hours only).
  • Scans rolling windows (3hr for Oil, 2hr for Nasdaq) ending in the last 2 hours
  • Only windows ending recently are checked — old spikes age out naturally, preventing duplicate alerts
  • Dedup safety net: tracks peak move % per ticker per day, only re-alerts if move grows by ≥1% more
  • Thresholds: Oil ≥3%, Nasdaq ≥2%

c) Forex Calendar (forex_calendar_alert.py)

  • Source: nfs.faireconomy.media (Forex Factory mirror)
  • Filters: USD currency only, High impact only (red events)
  • Sends a reminder 22-26 hours before the event
  • Shows event name, AEST time, ET time, forecast, and previous values
  • State tracked in forex_alert_state.json — only saves state after confirmed webhook success

Channel 2: SLACK_WEBHOOK_URL_CUSTOM

  • Receives custom team alerts from custom_alerts.py
  • Alert sent when UTC time is ≤30 minutes away

10. Data Pipeline & Infrastructure

GitHub Actions Workflow (update-data.yml)

Runs hourly. Steps execute sequentially:

  • update_data.py — Fetches daily ratio data (BTC, ETH, MSTR, BMNR) → data.json
  • backfill_hourly.py — Fetches hourly prices (BTC, FARTCOIN, SPX6900) → fartcoin_hourly.json, spx6900_hourly.json
  • backfill_liquidity.py — Fetches daily price + volume (BTC, FARTCOIN) → liquidity_daily.json, fartcoin_liquidity_daily.json. Has retry logic with 429 rate-limit handling (30s × attempt backoff)
  • Commit & push data files
  • detect_events.py — Run divergence detection, alert Slack on new events
  • forex_calendar_alert.py — Check for upcoming USD high-impact events
  • market_alerts.py — Check Oil & Nasdaq for threshold moves
  • custom_alerts.py — Check for due custom team alerts
  • Each alert script commits its own state file after running

Cloudflare Pages Functions (functions/_middleware.js)

All requests pass through the middleware, which handles:

  • Password protection: Basic Auth via CFP_PASSWORD env var
  • /api/yahoo: Proxies Yahoo Finance requests (bypasses CORS)
  • /api/polymarket: Proxies Polymarket API requests
  • /api/deribit: Proxies Deribit API requests
  • /api/alerts: GET/POST for custom alerts — reads/writes custom_alerts.json via GitHub Contents API using GITHUB_PAT and GITHUB_REPO env vars

Environment Variables

  • GitHub Secrets: SLACK_WEBHOOK_URL, SLACK_WEBHOOK_URL_CUSTOM
  • Cloudflare Pages: CFP_PASSWORD, GITHUB_PAT (fine-grained, Contents: Read+Write), GITHUB_REPO (owner/repo format)

11. Assumptions & Limitations

Timezone

  • All stored data is in UTC. Dates in data.json are UTC calendar dates (YYYY-MM-DD)
  • Hourly timestamps use ISO 8601 format (e.g. 2025-09-15T14:00:00Z)
  • AEST display mode shifts dates +1 day — this is a labelling shift, not a data recomputation. It reflects that a US market close on Monday UTC appears as Tuesday morning AEST
  • The UTC→AEST conversion for custom alerts may be off by ~1 hour near DST boundaries

Data Gaps & Quality

  • Missing hourly data points are plotted as gaps (no interpolation). Charts use spanGaps: true for line continuity across short gaps
  • CoinGecko free tier is rate-limited — backfill_liquidity.py includes 15s pauses between fetches and retry logic for 429 errors
  • If a data fetch fails, the script keeps existing data and continues (graceful fallback)
  • Yahoo Finance prices have a ~15-minute delay for live quotes

Divergence Detection

  • The 24-hour lookback is exactly 24 data points (hourly candles), not a sliding time window
  • Clustering treats gaps of ≤3 hours as the same event — two spikes 4 hours apart are separate events
  • One event per calendar day per analysis type (AEST date). If two divergences occur on the same AEST date, only the first is recorded
  • The 72-hour confirmation window starts from the end of the divergence cluster, not the start
  • Confirmed status is binary: crash/pump either hit the threshold or didn't. Partial moves below threshold are labelled "no crash/pump"

Market Alerts (Oil/Nasdaq)

  • Yahoo Finance range=1d returns data for the current trading session only. Outside market hours, data may be stale or unavailable
  • Rolling window scan only checks windows ending in the last 2 hours — spikes from earlier in the day that were already processed won't re-trigger
  • A legitimate second spike of similar magnitude on the same day may not re-alert unless it exceeds the prior alert's move by ≥1%

Alert Delivery

  • All Slack alerts depend on GitHub Actions running on schedule. GitHub does not guarantee exact cron timing — delays of 5-15 minutes are normal, occasionally longer during high load
  • Webhook state is only saved after confirmed delivery (HTTP 200). If the webhook fails, the alert will be retried on the next run
  • Custom alerts check for events due within 30 minutes. Combined with hourly runs, an alert may arrive up to ~90 minutes after the set time in worst case
  • Slack free tier has no webhook limits. Webhooks do not expire unless the Slack app is uninstalled

Polymarket Rate Odds

  • Event slugs are matched by pattern (e.g. fed-decision-in-april). If Polymarket changes their slug format, odds will fail silently and fall back to the static consensus table
  • The 6-month rate outlook is a static consensus table and must be manually updated as new forecasts are published
